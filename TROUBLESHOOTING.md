# Troubleshooting

Known gotchas from getting this project's dev environment stable, so nobody
(future Claude session included) has to rediscover them the hard way. Check
here first when something breaks in a confusing way; add to this file when
you find a new one.

## Always run `./dev.sh`, not two separate manual terminals

Running the backend and frontend in two independent terminal tabs means one
of them can silently die (crash, closed tab, machine sleep) while the other
keeps running -- and there's no single place that makes that obvious. You end
up debugging "why doesn't this work" for a while before realizing the answer
was just "one server wasn't running."

`./dev.sh` from the repo root starts both together, interleaves their
output with `[backend]` / `[frontend]` prefixes in one terminal, and Ctrl+C
stops both. If something's broken, check that output first -- a crashed
backend shows up right there instead of as a mystery on the frontend side.

## "Failed to fetch" in the tap-word card doesn't mean the network is down

For a while, ANY backend-side failure on `/api/word-info` -- a bug, a bad
API key, Anthropic being unreachable, anything -- surfaced to the user as
the exact same generic "Failed to fetch," regardless of the real cause. The
reason: an *unhandled* exception in a FastAPI route becomes a 500 response
generated by Starlette's `ServerErrorMiddleware`, which sits **outside**
the `CORSMiddleware` layer added in `main.py`. That 500 comes back with no
`Access-Control-Allow-Origin` header, the browser blocks it, and `fetch()`
reports that to JS as an opaque network failure -- the real status code and
message never reach the frontend at all.

Fixed in `main.py`'s `word_info_route`: exceptions are now caught inside the
route and returned as a normal `JSONResponse({"error": ...}, status=502)`,
which stays inside CORSMiddleware's path and reaches the frontend intact
(`useTapWord.ts` reads `body.error` and shows it in the popover). **If you
still see a literal "Failed to fetch" with no real message after this fix,**
that means the request never reached the backend at all -- check whether
`uvicorn` is actually running (see `dev.sh` output) before assuming it's a
code bug.

## `git add .` only stages the current directory, not the whole repo

`.` is scoped to wherever your shell's `cwd` is. If you're inside
`frontend/` and run `git add .`, changes to `../README.md` or files at the
repo root won't be staged -- `git status` will show them with a `../`
prefix, which is the tell that you're one directory too deep. Either `cd`
to the repo root before running git commands, or use `git add -A`, which
stages the whole repo regardless of cwd.

## Anthropic API connectivity

As of this writing: the backend fails with `anthropic.APIConnectionError:
Connection error.` when calling `/api/word-info`, even though `curl -v
https://api.anthropic.com` from a normal terminal connects fine (full TLS
handshake, real response). That mismatch points at something specific to
the Python environment rather than the network broadly -- leading
suspect is SSL certificate verification: Python's `httpx`/`certifi` don't
automatically trust whatever your OS or network already trusts, so on a
network that does TLS inspection (school/corporate VPN, Zscaler-style
proxy), `curl` (which trusts the OS keychain) can succeed while Python
fails. **Update this section once it's actually resolved** with the real
fix, so it's not lost.
